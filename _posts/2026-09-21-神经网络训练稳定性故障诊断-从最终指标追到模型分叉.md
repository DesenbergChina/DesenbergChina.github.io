## 前言

最近在做一个多随机种子监督学习实验时，我遇到了一类很典型、也很容易被“直接调参”掩盖的问题：

**同样的数据、同样的训练流程，只改变初始化种子，最终模型却明显分成了两类。**

最终验证指标可以告诉我：

- 哪些种子表现较好；
- 哪些种子表现较差；
- pinball loss、coverage、Spearman、结构违反率分别是多少。

但是它们不能回答更重要的问题：

> **这些模型究竟从训练的哪一步开始分开？又是哪种机制导致了分叉？**

当前最可疑的机制是输出头中的硬 `ReLU` 进入零梯度区间，但这仍然只是一个待验证假设。

如果在没有诊断证据的情况下直接把 `ReLU` 改成 `Softplus`，或者修改初始化、学习率、目标归一化、损失权重，确实可能让指标变好，但也可能：

- 只是碰巧救活某几个随机种子；
- 降低 pinball loss，却破坏其他目标；
- 改变词典序决策行为；
- 把真正的学习率或尺度问题掩盖掉。

所以这一轮工作的目标不是继续“试哪个修改有效”，而是先建立一套**训练过程诊断记录**。

---

## 1. 为什么最终指标不够

假设一个模型最终出现：

```text
Spearman = 0
```

单看这个结果，至少可能对应以下几种完全不同的原因：

1. 输出头进入硬 ReLU 死区，相关通道长期没有梯度；
2. 模型没有死亡，但逐渐预测成近似常数；
3. 标签中零值比例过高，模型学会了保守输出零；
4. 学习率过大，模型前期正常、后期才塌缩；
5. 联合损失的某一个分量压制了另一个分量；
6. 网络预测差异其实很小，只是在后续匹配决策边界附近被放大。

这些情况的**最终表现可以很像，但修复方法完全不同**。

例如：

- 死 ReLU 更适合检查初始化、正偏置或平滑正值变换；
- 后期塌缩更应检查学习率和更新过程；
- 常数预测要检查标签分布和联合损失；
- 决策边界敏感则应该分析匹配裕量，而不是继续改网络。

因此，最终指标适合做门禁，却不适合作为根因诊断工具。

---

## 2. 诊断真正要回答的两个问题

这次诊断只围绕两个问题展开：

### 问题一：模型什么时候开始分叉？

需要判断异常种子属于哪一种模式：

```text
初始化时就异常
    ↓
第一个 epoch 已经分开
```

还是：

```text
初始化正常
    ↓
训练前期接近
    ↓
若干 epoch 后突然分开
```

这两个结果直接对应不同的修复方向。

### 问题二：分叉时到底发生了什么？

需要记录训练过程中能够区分以下机制的信号：

- 原始输出进入负区间；
- ReLU 投影后大量变成零；
- 输出通道梯度消失；
- 梯度频繁触发裁剪；
- 某个 loss 分量开始占主导；
- 不同模块梯度尺度严重失衡；
- 网络输出仍接近，但下游匹配动作突然发生变化。

换句话说，**不是记录更多指标，而是记录能区分候选根因的指标。**

---

## 3. 最小诊断记录：不用每个 epoch 都保存

为了避免把一次故障诊断变成新的正式实验，我只建议记录少量关键节点：

```text
epoch = 0, 1, 2, 5, 10, 20, 50, 100
```

其中：

- `0`：优化器第一次更新之前；
- `1、2`：观察初始化是否立即造成分叉；
- `5、10、20`：定位中前期训练动态；
- `50、100`：观察是否属于后期塌缩或过拟合。

如果异常在第 2 个 epoch 就已经出现，就没有必要保存几十轮完整 checkpoint。

---

## 4. 建议记录哪些量

### 4.1 输出投影前的原始值

如果模型最终使用：

```python
y = relu(raw)
```

那么必须同时观察 `raw`，而不能只看 `y`。

建议按输出头或输出通道记录：

- mean；
- min / max；
- 负值比例；
- 正值比例；
- 接近零的比例。

最关键的问题是：

> 异常种子的原始输出是不是从一开始就大量落在 0 以下？

如果答案是肯定的，而且这些通道经过 ReLU 后同时没有梯度，那么“死区”就不再只是猜测。

---

### 4.2 投影后的零值比例和输出多样性

建议记录：

- 输出为 0 的比例；
- 各分位点均值；
- 预测唯一值数量；
- 中位数预测的方差；
- 不同样本预测差异。

例如，如果某个种子：

```text
raw output 大量为负
→ ReLU 后几乎全部为 0
→ prediction unique count 很低
→ Spearman 最终为 0
```

那么这些现象就形成了一条连续证据链，而不是只看到最后一个 `Spearman=0`。

---

### 4.3 输出头和不同模块的梯度

至少记录：

- 输出层权重梯度范数；
- 输出层 bias 梯度；
- 每个输出通道是否得到非零梯度；
- backbone / encoder / head 的梯度范数；
- 零梯度参数比例。

尤其要比较不同随机种子之间：

```text
encoder grad norm
head grad norm
urgent head grad norm
total head grad norm
```

如果不同模块长期相差几个数量级，问题可能不是激活函数本身，而是目标尺度或网络尺度不平衡。

---

### 4.4 梯度裁剪情况

如果训练使用 `clip_grad_norm_`，不能只知道“配置了梯度裁剪”，还应该知道它是否真的频繁生效。

建议记录：

- 裁剪前总梯度范数；
- 裁剪阈值；
- 是否发生裁剪；
- 各 epoch 的裁剪比例。

如果异常模型从某个 epoch 开始长期触发裁剪，就应优先怀疑优化更新不稳定，而不是初始化。

---

### 4.5 联合损失的各个分量

如果模型使用联合目标，不要只记录总 loss。

例如：

```text
total_loss
urgent_pinball
total_pinball
auxiliary_loss
regularization
```

否则即使看到总 loss 正常下降，也不知道是不是一个分量已经压制了另一个分量。

这对“零标签占多数”的任务尤其重要：模型可能通过预测接近零取得不错的平均损失，却牺牲了排序能力和非零目标的辨识能力。

---

### 4.6 标签分布与目标尺度

诊断训练动态之前，应先固定记录训练集本身的基本统计：

- 零标签比例；
- 非零标签比例；
- 均值 / 中位数 / 最大值；
- 不同目标分量的尺度；
- 不同场景或类别的分布。

这样才能判断：

> 模型输出大量为零，是网络死了，还是数据本身就在强烈奖励零预测？

---

### 4.7 下游决策裕量

如果网络输出还要进入 Hungarian Matching、MILP 或词典序选择，那么预测误差和最终动作之间并不是线性关系。

可能出现：

```text
预测差异很小
↓
两个候选方案成本非常接近
↓
跨过匹配边界
↓
最终动作完全不同
```

因此，还应记录适当的**决策裕量**，例如：

- 最优方案与次优方案的成本差；
- 候选动作之间的 score gap；
- 网络预测扰动前后是否发生匹配翻转。

如果模型输出差异很小，但动作突然变化，那么问题可能在决策边界附近，而不是训练网络本身已经“坏掉”。

## 5. 观察结果如何直接指导修复

| 观察到的现象 | 更可能说明什么 | 优先修复方向 |
|---|---|---|
| 初始原始输出大量为负，投影后为零，相关梯度也接近零 | 输出头进入 ReLU 死区 | 正偏置安全初始化，或评估 Softplus 等平滑正值变换 |
| 开始时正常，若干 epoch 后突然变成零输出 | 更新过大，把输出推入死区 | 学习率预热、降低输出头学习率、检查优化器 |
| 梯度长期被裁剪 | 优化过程不稳定 | 降低学习率、重新检查目标尺度或裁剪阈值 |
| 输出头仍有梯度，但预测逐渐变成相同值 | 常数解或零标签主导 | 检查损失权重、标签分布、非零辅助目标 |
| 不同模块梯度相差几个数量级 | 网络或目标尺度失衡 | 标签/输出归一化、分组学习率 |
| 多个种子前期接近，后期才分开 | 训练过久或后期过拟合 | 早停、学习率衰减、选择稳定 checkpoint |
| 预测值差异很小，但最终动作突然改变 | 决策位于匹配边界附近 | 分析匹配裕量，而不是继续修改网络 |

这个表的意义是把：

```text
“我想试一下 Softplus”
```

改成：

```text
“日志显示初始 raw 输出长期为负，
对应通道从第一个 batch 起没有梯度，
所以需要消除硬 ReLU 死区。”
```

两者在工程可信度和论文证据强度上完全不同。

## 6. 一个推荐的 JSONL 诊断格式

诊断记录最好是机器可读的，而不是只打印到终端。

例如每个观测 epoch 写一行：

```json
{
  "seed": 5102,
  "epoch": 20,
  "train_loss": 0.0138,
  "validation_pinball": 0.0154,
  "raw_output": {
    "urgent_positive_fraction": 0.12,
    "urgent_negative_fraction": 0.88
  },
  "projected_output": {
    "urgent_zero_fraction": 0.91,
    "median_prediction_std": 0.0004
  },
  "gradient": {
    "encoder_norm": 0.018,
    "head_norm": 0.0002,
    "zero_grad_head_fraction": 0.75
  },
  "clipping": {
    "pre_clip_norm": 3.7,
    "threshold": 1.0,
    "clipped": true
  },
  "loss_components": {
    "urgent_pinball": 0.0021,
    "total_pinball": 0.0117
  }
}
```

这样后续可以直接比较：

```text
seed 5101 vs 5102
seed 5103 vs 5104
epoch 0 vs 20
```

也方便生成折线图、箱线图和论文附录。

## 7. PyTorch 中的轻量实现思路

这里不需要保存完整计算图或整个 checkpoint，只需要在指定 epoch 做一次统计。

例如：

```python
DIAGNOSTIC_EPOCHS = {0, 1, 2, 5, 10, 20, 50, 100}

if epoch in DIAGNOSTIC_EPOCHS:
    diagnostics = {
        "seed": seed,
        "epoch": epoch,
        "head_grad_norm": model.head.weight.grad.norm().item()
            if model.head.weight.grad is not None else 0.0,
        "head_zero_grad_fraction": (
            (model.head.weight.grad == 0).float().mean().item()
            if model.head.weight.grad is not None else 1.0
        ),
    }

    with torch.no_grad():
        raw = get_raw_head_output(...)
        projected = project_output(raw)

        diagnostics["raw_negative_fraction"] = (
            (raw < 0).float().mean().item()
        )
        diagnostics["projected_zero_fraction"] = (
            (projected == 0).float().mean().item()
        )
```

工程上更稳妥的做法是：

- 使用 forward hook 读取投影前的输出；
- 在 `optimizer.step()` 之前读取梯度；
- 在 `clip_grad_norm_` 前记录原始梯度范数；
- 只在关键 epoch 运行额外统计；
- 将结果写入独立的 `diagnostics/*.jsonl`。

这样不会改变正常训练语义。

## 8. 诊断记录不应该改变正式实验

为了保证诊断仍然能够解释现有实验，我认为这类记录应满足几个约束：

- 不改变训练数据；
- 不改变训练/验证划分；
- 不改变共享 batch 顺序；
- 不改变 loss；
- 不改变模型输出；
- 不额外调用随机数从而影响后续训练；
- 不进入正式实验门禁指标；
- 不覆盖原有训练产物。

它只是**观测现有训练过程**。

因此，这类诊断可以作为一次性的故障排查运行，不需要像论文正式实验一样扩大种子数量或重新做整套统计显著性分析。

---

## 9. 如何判断 ReLU 死区假设是否成立

以异常种子 `5102/5104` 为例，可以设计一个非常明确的判据。

### 情况 A：第一个 epoch 就死亡

如果发现：

```text
epoch 0:
raw 输出大量 < 0

epoch 1:
ReLU 后大量 = 0
对应输出通道梯度 = 0

之后:
这些通道一直没有恢复
```

那么可以相当有力地支持：

> 初始化使部分输出头进入硬 ReLU 零梯度区间，训练无法把它们重新拉回有效区域。

此时正偏置初始化或平滑非负投影就是有针对性的修复。

### 情况 B：前期正常，第 20 个 epoch 才塌缩

如果日志显示：

```text
epoch 0~10:
输出正常
梯度正常
种子之间接近

epoch 20:
梯度突然增大并频繁裁剪
raw 输出整体跨入负区间

epoch 20 之后:
输出逐渐归零
```

那么修改初始化并不能解决真正的问题。

更合理的方向是：

- 降低学习率；
- 增加 warm-up；
- 降低输出头学习率；
- 检查 loss 尺度和梯度爆发。

### 情况 C：输出没有死亡，但最后都变成常数

如果：

- 输出头始终有梯度；
- raw 值并没有长期处于负区间；
- 预测方差却不断下降；
- 零标签占比很高；

那么应优先检查数据分布和联合 loss，而不是归咎于 ReLU。

## 10. 为什么这比依次盲试修改更重要

如果没有诊断，常见做法往往是：

```text
先改初始化
→ 不行再改 Softplus
→ 再做归一化
→ 再降学习率
→ 再调 loss 权重
```

最终即使某一次实验变好了，也很难回答：

> 到底是哪一个机制被修复了？

而训练诊断把流程改成：

```text
提出候选机制
↓
设计能区分这些机制的观测量
↓
找到分叉发生的 epoch
↓
找到同时发生的输出/梯度/损失变化
↓
只修改对应机制
↓
重新执行固定正式实验
```

这样做的收益不仅是减少试验次数。

更重要的是，它可以让最终报告写成：

> 训练过程诊断显示，异常随机种子在训练早期即出现特定输出通道的负原始激活，经过硬 ReLU 投影后形成持续零输出，并伴随对应输出头梯度消失。因此后续修复针对该零梯度机制，而不是依据最终验证指标进行事后超参数搜索。

这比“换成 Softplus 后效果更好”更接近真正可解释、可复现的实验结论。

---

## 11. 最终诊断清单

以后再遇到“不同随机种子最终明显分成两类”的情况，我会先检查：

- [ ] epoch 0 的原始输出分布是否已经不同；
- [ ] 输出投影后零值比例是否异常；
- [ ] 各输出通道是否都有梯度；
- [ ] encoder 与 head 梯度尺度是否接近；
- [ ] 是否长期触发梯度裁剪；
- [ ] 联合 loss 的某个分量是否开始占主导；
- [ ] 标签零值比例和目标尺度是否合理；
- [ ] 模型预测是否逐渐变成常数；
- [ ] 分叉发生在训练前期还是后期；
- [ ] 下游动作变化是否只是匹配边界敏感；
- [ ] 修复是否能由诊断记录直接解释。

---

## 结语

多随机种子训练不稳定时，最容易犯的错误是把“最终哪个种子失败了”当成“已经知道为什么失败”。

真正有用的诊断，需要把最终指标往前追：

```text
最终指标异常
→ 预测何时开始分叉
→ 输出分布发生什么变化
→ 梯度是否仍然存在
→ 哪个 loss 或更新机制先发生异常
→ 下游决策是否放大了微小预测差异
```

因此，增加诊断记录的实际作用并不是产生更多日志，而是：

**避免盲目依次尝试初始化、Softplus、归一化、学习率和损失权重，并为最终选择某项修复提供可以复现、解释和写进论文的因果证据。**
